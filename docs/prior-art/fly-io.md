# fly.io — architecture notes
_Research date: 2026-09-03. Sources are linked inline; "(inferred)" marks anything not stated verbatim by Fly._

## One-paragraph summary

Fly.io is a global Firecracker-microVM platform whose orchestration is deliberately *not* a scheduler: every worker runs `flyd`, a Go daemon that is "the source of truth for all the VMs running on a particular worker" and keeps its state as durable finite-state-machine invocations in a local BoltDB log ([carving](https://fly.io/blog/carving-the-scheduler-out-of-our-orchestrator/), [JP exit interview](https://fly.io/blog/the-exit-interview-jp/)). A stateless broker, `flaps`, serves the Machines REST API by asking regional `flyd`s for capacity and placing synchronously — "you're going to get VMs in MAD, or you're going to get nothing" ([carving](https://fly.io/blog/carving-the-scheduler-out-of-our-orchestrator/)). Fleet-wide state (which Machine is where, its status) is replicated with **Corrosion**, a Rust SWIM-gossip + cr-sqlite CRDT SQLite, which replaced Consul after Consul drove ">10 gb/sec" of traffic and double-digit-second DNS lag ([foolish consistency](https://fly.io/blog/a-foolish-consistency/), [corrosion](https://fly.io/blog/corrosion/)). A Rust Anycast router, **fly-proxy**, runs on every edge and worker, reads Corrosion for routing, terminates TLS, backhauls over a WireGuard mesh, wakes stopped/suspended Machines on demand, and honours `fly-replay` ([fly-proxy docs](https://fly.io/docs/reference/fly-proxy/)). Machines are OCI images unpacked by a per-host `containerd` on an LVM2 thin pool into block devices, booted with Fly's Rust init (now `pilot`, an OCI runtime) ([docker-without-docker](https://fly.io/blog/docker-without-docker/)). Volumes are host-pinned NVMe slices, which Fly itself calls the thing that "anchors workloads to specific physicals" and cost 3 years of migration work; their 2025–26 sandbox product **Sprites** discards both the per-tenant image pull and host-pinned storage in favour of pre-pooled VMs and a JuiceFS-style chunked filesystem on object storage with Litestream-backed SQLite metadata ([sprites design](https://fly.io/blog/design-and-implementation/)). Fly's big outages (Sep 1 2024, Oct 22 2024, Nov 25 2024) all trace to the "global, flat, unsegmented topology" of Corrosion + fly-proxy, and their fix has been regionalising Corrosion, adding watchdogs, and circuit-breaking gossip ([infra-log 2024-09-07](https://fly.io/infra-log/2024-09-07/), [2024-10-26](https://fly.io/infra-log/2024-10-26/), [2024-11-30](https://fly.io/infra-log/2024-11-30/)).

Who owns what (all stated in the linked posts unless marked):
- **Machine truth**: the worker's `flyd` ([carving](https://fly.io/blog/carving-the-scheduler-out-of-our-orchestrator/)). Migration broke this assumption and required Corrosion design changes ([machine-migrations](https://fly.io/blog/machine-migrations/)).
- **Routing truth**: each host's local Corrosion replica, consumed by fly-proxy and corro-dns ([fly-proxy docs](https://fly.io/docs/reference/fly-proxy/), [infra-log](https://fly.io/infra-log/)).
- **Placement**: `flaps`, synchronously, per request ([carving](https://fly.io/blog/carving-the-scheduler-out-of-our-orchestrator/)).
- **Account/app/org truth**: central Rails/Elixir API + Postgres — "Preflight check with centralized Virginia database" ([fly-machines](https://fly.io/blog/fly-machines/)); Machine *creates* (not start/stop) still depended on Consul as late as Oct 2024 ([infra-log 2024-10-26](https://fly.io/infra-log/2024-10-26/)).

## 1. Fly Machines

**What it is.** "Fly Machines are VMs with a fast REST API that can boot instances in about 300ms" ([fly-machines blog](https://fly.io/blog/fly-machines/)); docs say "fast-launching VMs; they can be started and stopped at subsecond speeds" ([docs/machines](https://fly.io/docs/machines/)). A Machine is pinned to one physical host; there is no automatic failover — Fly's guidance is client-side: "Start machine X in Chicago. If that fails, Start machine Z in New Jersey" ([fly-machines blog](https://fly.io/blog/fly-machines/)).

**API.** `GET/POST /v1/apps/{app}/machines`, `/start`, `/stop`, `/suspend`, `/wait` (default timeout 60s; states `started|stopped|suspended|destroyed`; 408 on timeout), leases (exclusive lock, nonce in `fly-machine-lease-nonce`, 409 on conflict), cordon/uncordon, metadata, exec ([machines-resource docs](https://fly.io/docs/machines/api/machines-resource/)). `region` and `name` are immutable after create; "Create and update requests can fail; you're responsible for retry logic" (same).

**States.** Persistent: `created, started, stopped, suspended, failed`; transient: `creating, starting, stopping, restarting, suspending, destroying, launch_failed, updating, replacing`; terminal: `destroyed, replaced, migrated`. Docs say to investigate if transient >5 min (>10 min for updating) ([machine-states](https://fly.io/docs/machines/machine-states/)).

**Create vs start — the design that makes it fast.** Create is the expensive path (image pull, placement, "92 steps" incl. "Preflight check with centralized Virginia database" and "NATS broadcast reserving capacity on target hosts"); start is a direct message to the owning host, "~10ms" LAX→LAX to "~150ms" LAX→GRU API latency, because "The host already has the image cached locally" ([fly-machines blog](https://fly.io/blog/fly-machines/)). Their explicit product advice: "create machines ahead of time and start them when you need them"; a stopped Machine costs storage only ("$0.15/mo for a 1GB Docker image") (same). Idle detection is pushed *into* the guest: "Your in-machine process has a strongly-consistent view of local activity and can confidently detect idle" (same). The functions doc gives a default 120s idle-exit and notes start "clear[s] filesystem changes" (rootfs reset) ([functions-with-machines](https://fly.io/docs/machines/guides-examples/functions-with-machines/)).

**Image → rootfs.** Images are pushed to Fly's own registry (a wrapped Docker Go registry with token→org rewriting). On each worker, images are "pull[ed] from the registry into our server-local `containerd`, configured to run on an LVM2 thin pool"; the devicemapper snapshotter turns the unpacked layers into a synthetic block device; a second block device carries kernel + init + config; Volumes attach as LUKS block devices ([docker-without-docker](https://fly.io/blog/docker-without-docker/)). Result: "the VM build-and-boot process on a second deployment is faster than the logging" (same). A stop does a containerd snapshot reset that "can sometimes take 100-200ms" ([community 7022](https://community.fly.io/t/machines-take-3-8s-to-start-when-hitting-them-during-shutdown/7022)).

**Init.** Originally a Rust init (`init-snapshot`, open-sourced) that mounts filesystems, writes resolv.conf for 6PN, spawns an SSH server for WireGuard access, and runs the entrypoint from injected config ([docker-without-docker](https://fly.io/blog/docker-without-docker/)). Replaced by **`pilot`**: "Fly.io's new init, and more importantly, is itself a complete OCI runtime that can natively run containers inside of Fly Machines", with "an API for flyd to drive" ([JP exit interview](https://fly.io/blog/the-exit-interview-jp/)). Fly *also* discovered that images are a scheduling resource: "The set of images cached and ready to deploy on any given server is changing every second" ([carving](https://fly.io/blog/carving-the-scheduler-out-of-our-orchestrator/)).

**Gotchas Fly states.** Cold start of a real app is "~2+ seconds for common apps" ([suspend-resume docs](https://fly.io/docs/reference/suspend-resume/)); "Tiny images boot in under 2 seconds; larger, complex images are significantly slower" ([functions doc](https://fly.io/docs/machines/guides-examples/functions-with-machines/)); create P90 "sub-5-seconds for pretty much every region except for Johannesburg and Hong Kong" ([JP](https://fly.io/blog/the-exit-interview-jp/)); community-measured "the machine is created and started within 5 seconds, and on average, it takes around 20 seconds" ([community 22647](https://community.fly.io/t/why-machines-take-a-lot-of-time-to-be-created-sometimes/22647)). Sprites post is blunt: "Fly Machines take 'over a minute' to create ... Most of what's slow about creating a Fly Machine is containers" ([sprites design](https://fly.io/blog/design-and-implementation/)).

## 2. flyd + the orchestration model

**flyd.** "the source of truth for all the VMs running on a particular worker"; "keeps a boltdb database of its current state, which is an append-only log of all the operations applied to the worker"; "Nothing in flyd is cached; everything is just materialized on-demand from disk"; "If we bounce flyd, it picks up right where it left off" ([carving](https://fly.io/blog/carving-the-scheduler-out-of-our-orchestrator/)). It "is rigidly structured as a collection of state machines, like 'create a machine' or 'delete a volume', with each having a concrete representation both in the code (using Go generics) and in boltdb"; "An FSM step might be something like 'assign a local IPv6 address to this interface', or 'check out a block device with the contents of this container'" (same). JP: "a server for on-demand instances of durable finite state machines"; the design requirement was "we would need to deploy flyd all day, every day. If flyd was in the middle of doing some work, it needed to pick back up right where it left off, post-deploy"; BoltDB over SQL was chosen "to limit scope and prevent accidental state corruption fleet-wide" ([JP](https://fly.io/blog/the-exit-interview-jp/)).

**Placement — the exact model.** "flyd operates like a market. Requests to schedule jobs are bids for resources; workers are suppliers. Our orchestrator sits in the middle like an exchange." For a create in SYD, "`flaps` collects capacity information from all the flyds in SYD, and then runs a quick best-fit ranking over the workers with space, which is just a simple linear interpolation ranking workers as more or less desirable at different utilizations of different resources." There is no pending queue: "If you ask for VMs in MAD, you're going to get VMs in MAD, or you're going to get nothing" ([carving](https://fly.io/blog/carving-the-scheduler-out-of-our-orchestrator/)). `flaps` is "a stateful proxy for all the flyd instances" whose instances "don't hold on to any state; the different flaps instances around the world don't agree on a picture of the world" (same). The Machines API surfaces this as hard failures with client-side fallback: "if any specified region lacks capacity, the entire scale operation fails ... It's all or nothing"; per-Machine ops accept an ordered region list and "tries each in order until it finds one that works" ([machine-placement](https://fly.io/docs/machines/guides-examples/machine-placement/)). (inferred) "hosts refuse" in Fly terms = a flyd reporting no capacity / the reservation failing at the host, and flaps moving on or returning an error; Fly does not describe a two-phase reserve/commit beyond "NATS broadcast reserving capacity on target hosts" ([fly-machines blog](https://fly.io/blog/fly-machines/)).

**Why they left Nomad.** Synchronous scale-from-zero: Nomad's "asynchronous consensus-based scheduling" could not place within a request. Autoscaling: 15s metric scrape "plus Nomad's scheduling work adds a bunch of time on top". Bin packing "is wrong for platforms like Fly.io" → "Katamari Damacy scheduling, where a couple overworked servers in our fleet suck up all the random jobs." "We Run One Global Cluster" whereas Nomad wants federated regional clusters ([carving](https://fly.io/blog/carving-the-scheduler-out-of-our-orchestrator/)).

**Operational lessons (infra-log).** flyd's event store can bloat until "flaps timed out the request before it completed" (ORD, Mar 26 2026); flyd got "stuck restarting because its systemd service was waiting for nftables to reload" (Aug 13 2026); a mid-migration volume extend "could target the temporary clone device" until a missing FSM step was added ([infra-log index](https://fly.io/infra-log/), [2024-11-09](https://fly.io/infra-log/2024-11-09/)). "Control-plane Machines didn't auto-start" with "insufficient resources" (Aug 20 2026) — even Fly's own managed Postgres depends on autostart placement succeeding ([infra-log](https://fly.io/infra-log/)).

**Migration (Making Machines Move).** Coordinator FSM in flyd: stop source → tell target flyd → target starts `dm-clone` over the network (NBD abandoned: "we kept getting stuck nbd kernel threads when there was any kind of network disruption" → iSCSI) → boot on the clone → background hydration → convert to linear device; DISCARD/fstrim marks unused blocks hydrated. "By summer of 2024, we got to where our infra team can pull 'drain this host' out of their toolbelt without much ceremony." Cost: broke the "workers are the source of truth" assumption in Corrosion (race conditions → design changes) and 6PN addresses that "refer in part to specific worker servers" ([machine-migrations](https://fly.io/blog/machine-migrations/)).

## 3. Corrosion

**What/why.** "Corrosion is a Rust program that propagates a SQLite database with a gossip protocol." Rationale: consensus "break[s] down over long distances" and wastes effort agreeing on updates that "couldn't conflict in the first place"; model is link-state routing (OSPF): "routers are sources of truth for their own links and responsible for quickly communicating changes to every other router." "No locking, no central servers, and no distributed consensus." Conflicts are rare because "workers own their own state, so updates from different workers almost never conflict" ([corrosion](https://fly.io/blog/corrosion/)). Consul before it: ">10 (t-e-n) gb/sec of Consul traffic", a bug where "updates anywhere in Consul un-blocked every long-polling query", and DNS "double-digit second delays after instances came up — or worse, after they terminated" ([foolish consistency](https://fly.io/blog/a-foolish-consistency/)). Local read cost is the point: ">= 300ms for a round-trip to something on the other side of the world ... usually takes less than 1ms from a local source" ([corrosion README](https://github.com/superfly/corrosion)).

**Mechanics.** cr-sqlite marks tables CRDT-managed; per-column changes land in `crsql_changes`, are batched and gossiped; LWW "using logical timestamps"; membership is SWIM via `foca`; transport QUIC; periodic anti-entropy sync with random subsets; HTTP API for local exec/query; NDJSON **subscriptions** to SQL queries with monotonically increasing `change_id` and `from=` resume (lagging clients are disconnected with a fatal error; root-level ORDER BY is not honoured for changes); Rhai templates that rewrite config files on change ([corrosion blog](https://fly.io/blog/corrosion/), [subscriptions doc](https://superfly.github.io/corrosion/api/subscriptions.html), [README](https://github.com/superfly/corrosion/blob/main/README.md)). Schema rules: only `CREATE TABLE`/`CREATE INDEX`, additive only, no column/table drops, primary key required and non-null, "All non-nullable columns require defaults", no unique indexes other than the PK; Corrosion diffs schema files on reload ([schema doc](https://superfly.github.io/corrosion/schema.html)). Quick-start caveat: "cr-sqlite creates 1 change per column 'changed' in a row" ([quick-start](https://superfly.github.io/corrosion/quick-start.html)).

**What is in it / not in it.** In: Fly Machine state and config, app→region map (global cluster), per-Machine detail (regional clusters), service catalog for fly-proxy and DNS, health, org/app metadata (the May 2026 incident was "organization updates ... fail to be propagated to Corrosion") ([corrosion blog](https://fly.io/blog/corrosion/), [infra-log](https://fly.io/infra-log/)). Not in: macaroon tokens (`tkdb`, SQLite + Litestream), secrets (Pet Sematary), load (NATS gossip) — "Not every piece of state we manage needs gossip propagation" ([corrosion blog](https://fly.io/blog/corrosion/), [foolish consistency](https://fly.io/blog/a-foolish-consistency/)).

**Operational lessons Fly paid for (chronological).**
- May 2024: edge capacity pressure in FRA "degrade[s] the performance both of Corrosion... and NATS"; a worker decommission produced a Corrosion update that left ghost entries in `udpcatalogd` eBPF maps ([2024-05-25](https://fly.io/infra-log/2024-05-25/)).
- Aug 2024: added "queue caps to prevent unbounded queues" and fixed "a bug that was causing Corrosion to request way more data than it needs when syncing up a new node" ([2024-08-24](https://fly.io/infra-log/2024-08-24/)).
- Sep 1 2024: a customer's virtual-services config "propagated within seconds to all fly-proxy instances via Corrosion" and hit an `if let` RWLock deadlock — the worst outage in their history. "The 'original sin' of this design is that it operates in a global, flat, unsegmented topology" ([2024-09-07](https://fly.io/infra-log/2024-09-07/)).
- Oct 22 2024: expired Consul CA; flyd "queueing state updates and retrying them on an exponential backoff timer" → "corrosion is driving 150gB/s of traffic, saturating switch links"; restored Corrosion from daily snapshot + re-seed. Lesson: "no more half-measures" ([2024-10-26](https://fly.io/infra-log/2024-10-26/)).
- Nov 25 2024: adding a nullable column to the largest table "backfilled every row in the table with the default null value" → "tens of gigabytes of traffic"; hours to re-seed from the external source of truth. Fixes: "comprehensive circuit-breaker limits to Corrosion", OS-level rate limits, a re-seed runbook, and **regionalisation** so "most problems can be contained to a single region" ([2024-11-30](https://fly.io/infra-log/2024-11-30/)).
- Dec 12 2024: same `if let` bug class resurfaced after a Corrosion update; the watchdog limited it to minutes; semgrep rules added ([2024-12-14](https://fly.io/infra-log/2024-12-14/)).
- 2026: Corrosion OOMs with stuck systemd units (Jun 23), post-migration stale SQLite stats → lock contention → 502s (Jun 25), proxy/Corrosion schema skew leaving Machines unroutable in SIN (May 19), org updates lost when the API deployed before the global schema (May 30), fly-proxy lazy-loader over Corrosion subscriptions reaching "500 ms to several seconds" under load (May 28) ([infra-log index](https://fly.io/infra-log/)).
- Design responses: publish the *whole* Machine record rather than incremental deltas ("re-publish the entire data set for the Machine"); Tokio watchdogs in every service ("an event-loop stall will bounce the service and make a king-hell alerting racket"); Antithesis deterministic testing; checkpoint backups on object storage with the ability to "rebuild from worker sources of truth" ([corrosion blog](https://fly.io/blog/corrosion/)).

## 4. Suspend / resume

**Mechanics.** "Suspending a Machine pauses the Machine and takes a snapshot of its state, including its memory"; implemented with Firecracker snapshots that "capture the entire VM state: CPU registers, memory contents, open file handles" ([suspend-resume docs](https://fly.io/docs/reference/suspend-resume/), [preview thread](https://community.fly.io/t/new-feature-in-preview-suspend-resume-for-machines/20672)). Resume spawns a *new* Firecracker process and loads the snapshot over the API socket; a bind/listen race made 0.6% of resumes fail with "machine exited with exit code 0, not restarting" until the supervisor retried on ECONNREFUSED ([more-reliable-resumes](https://community.fly.io/t/more-reliable-machine-resumes/26007)).

**Numbers.** Resume "a few hundred ms" vs cold start "~2+ seconds for common apps" ([docs](https://fly.io/docs/reference/suspend-resume/)); staff-observed "~250ms resume time, later improving to ~100ms" with "natural variation" from "memory snapshot caching" ([autosuspend thread](https://community.fly.io/t/autosuspend-is-here-machine-suspension-is-enabled-everywhere/20942)); Fly's tweet: "Fly Machines can boot in 250ms" ([x.com](https://x.com/flydotio/status/1818017404007452806)).

**Limits.** "≤ 2 GB" memory ("For larger memory sizes, suspend is discouraged due to increased suspend times" — "the system writes entire memory contents to disk"), no swap, no schedule, no GPU (different hypervisor), updated since 2024-06-20 ([docs](https://fly.io/docs/reference/suspend-resume/), [threads](https://community.fly.io/t/autosuspend-is-here-machine-suspension-is-enabled-everywhere/20942)). Machines over the limit "fall back to autostop". Fly floated Firecracker "diff" snapshots for larger Machines (same thread). Suspend "does not free region capacity — Suspended machines still reserve their resources" ([docs](https://fly.io/docs/reference/suspend-resume/)).

**Not durable, single-use.** Snapshots are "disposable — machines cannot resume from the same snapshot twice (security consideration) and will cold-start if migrated to different hosts" ([preview thread](https://community.fly.io/t/new-feature-in-preview-suspend-resume-for-machines/20672)); "Snapshots are tied to the exact code and state of the machine they were taken from" and a deploy invalidates them; "Fly does not guarantee that a suspended machine will resume" ([docs](https://fly.io/docs/reference/suspend-resume/)). Mass suspends hurt: "Large amount of machines suspending at once" saturated a SYD host's disk I/O (Apr 8 2026) ([infra-log](https://fly.io/infra-log/)).

**What breaks on resume.** "the machine thinks its network connections are still live. External systems (databases, APIs) may disagree" → ECONNRESET, pool errors; "the clock can lag a few seconds until NTP syncs"; "Some logs may be lost" (vsock `Broken pipe (os error 32)`); a vsock reconnection issue blocked follow-up requests "for 3-4 seconds"; no pre-suspend signal to the app; unlike stop, suspend "does not reset the machine's rootfs" ([docs](https://fly.io/docs/reference/suspend-resume/), [autosuspend thread](https://community.fly.io/t/autosuspend-is-here-machine-suspension-is-enabled-everywhere/20942)).

**Wake-on-request.** `auto_stop_machines = "off"|"stop"|"suspend"`, `auto_start_machines = bool`, `min_machines_running` (primary region only). "The Fly Proxy's stop loop runs every few minutes and stops at most one Machine per region per pass"; excess capacity is judged against `soft_limit` ([autostop docs](https://fly.io/docs/launch/autostop-autostart/)). Staff: idle threshold "approximately 5-7 minutes" ([autosuspend thread](https://community.fly.io/t/autosuspend-is-here-machine-suspension-is-enabled-everywhere/20942)). Autostart is request-driven: "Fly's proxy itself tries to wake machines for HTTP requests" — including bot hits ([remote-ide](https://fly.io/blog/remote-ide-machines/)). (inferred) The request is held by fly-proxy until the Machine reports started, then forwarded; Fly's docs do not describe a waiting page or a queue-timeout figure. Older stop/start round trips measured by a user: "~400-600ms to wake and respond" when fully stopped, "3-8 seconds" when hit mid-shutdown ([community 7022](https://community.fly.io/t/machines-take-3-8s-to-start-when-hitting-them-during-shutdown/7022)).

## 5. Fly Proxy

**Role/placement.** "Every server in our infrastructure runs a Rust-based proxy named fly-proxy" handling "accepting client connections, matching them to customer applications, applying handlers (eg: TLS termination), and backhaul between servers" ([architecture docs](https://fly.io/docs/reference/architecture/)). Edges "exist almost solely to run a Rust program called fly-proxy, the router at the heart of our Anycast network" ([taming-rust-proxy](https://fly.io/blog/taming-rust-proxy/)). Flow: Anycast → nearest edge → header injection, HTTPS redirect → WireGuard backhaul to "the closest healthy worker hosting the app's Machines" → worker-side fly-proxy delivers locally ([fly-proxy docs](https://fly.io/docs/reference/fly-proxy/)).

**Discovery.** "Fly Proxy retrieves routing intelligence from 'corrosion, our service catalog' using 'gossip-based service discovery'" (same). Originally it held in-memory state for every app fleet-wide; Nov 2024 moved to lazy-loading Corrosion state "to reduce memory footprint and brittleness" ([2024-11-09](https://fly.io/infra-log/2024-11-09/)); that lazy loader later showed "runaway queuing behavior at high load" with "infinite queues waiting on sqlite connections" (May 28 2026) and SQLite lock contention at ORD edges (Apr 12 2026) ([infra-log](https://fly.io/infra-log/)).

**Load balancing.** "Send traffic to the least loaded, closest Machine"; closeness = measured RTT edge→worker; `hard_limit` blocks new traffic, `soft_limit` prefers other Machines; "Soft limits operate only within regions"; cross-region failover only when local Machines are unhealthy or at hard limit; over hard limit requests queue then 503; `type = "requests"` pools connections ~4s ([load-balancing docs](https://fly.io/docs/reference/load-balancing/)). Load hints come via NATS, "neither consistent nor reliable" by design ([foolish consistency](https://fly.io/blog/a-foolish-consistency/)).

**fly-replay.** Response header the proxy acts on: `region=`, `instance=`, `prefer_instance=`, `app=`, `state=` (echoed in `fly-replay-src` with instance, region, µs timestamp), `elsewhere=true`, `timeout=`, `fallback=force_self|prefer_self`; "Requests larger than 1MB cannot be replayed"; fallback requests cannot themselves replay; request headers `fly-prefer-region`, `fly-force-region`, `fly-force-instance-id` ([dynamic-request-routing docs](https://fly.io/docs/networking/dynamic-request-routing/), [how-to-fly-replay](https://fly.io/blog/how-to-fly-replay/)). Regionalising Corrosion required "adapting fly-replay functionality for environments where proxies lack complete instance visibility" ([2024-12-14](https://fly.io/infra-log/2024-12-14/)).

**TLS/certs.** Let's Encrypt; challenges tls-alpn-01 (primary; "the Fly Rust proxy intercepts this ACME ALPN connection, retrieves the corresponding challenge certificate from storage"), http-01, dns-01 for wildcards; "Every application gets a unique, routable IPv6 address, and we won't attempt Lets Encrypt validation unless the target hostname resolves via CNAME to that IPv6 address" (subdomain-takeover defence); certs live in "our distributed certificate storage" ([how-cdns-generate-certificates](https://fly.io/blog/how-cdns-generate-certificates/), [custom-domain docs](https://fly.io/docs/networking/custom-domain/)). `_fly-ownership` TXT for CDN-fronted domains.

**Handlers.** http, tls, pg_tls, proxy_proto, raw TCP passthrough ([fly-proxy docs](https://fly.io/docs/reference/fly-proxy/)).

**Failure modes they hit.** Sep 1 2024 deadlock (above); Rustls CloseNotify busy-loop pegging CPU under Tigris load tests ([taming-rust-proxy](https://fly.io/blog/taming-rust-proxy/)); a `parking_lot` `try_write_for` race corrupting the lock word to `0xFFFFFFFFFFFFFFFF` ([parking_lot post](https://fly.io/blog/parking-lot-ffffffffffffffff/)); cordoned Machines still eligible for replay (Jun 15 2026); affinity replay returning empty Machine lists (Apr 28 2026) ([infra-log](https://fly.io/infra-log/)). Planned mitigations: shard fly-proxy so a bad config hits "1/N customers", shard internal services off the customer path, watchdog "like a pacemaker" ([2024-09-07](https://fly.io/infra-log/2024-09-07/)).

## 6. Networking

**6PN.** ULA `fdaa::/16`; each org a /48; per Machine a /112: 16b prefix | 32b org network | 32b host | 32b machine | 16b free ([private-networking docs](https://fly.io/docs/networking/private-networking/), [ipv6-wireguard-peering](https://fly.io/blog/ipv6-wireguard-peering/)). "We use that space to embed routing and access information; an identifier for your organization, an identifier for the Fly host that your app is running on, and an identifier for the individual instance" ([6pn blog](https://fly.io/blog/incoming-6pn-private-networks/)). Consequence Fly regrets: addresses encode the host, so migration invalidates them; they shipped "network address mappings to keep old 6PN addresses reachable" then a "stable 6PN" implementation, and in Jun 2026 "old-style DNAT rules actually override new-style stable 6PN's rewriting logic" ([machine-migrations](https://fly.io/blog/machine-migrations/), [infra-log](https://fly.io/infra-log/)). Docs now warn "6PN addresses are not static" and to use `<machine_id>.vm.<app>.internal` ([private-networking docs](https://fly.io/docs/networking/private-networking/)).

**Mesh.** "connectivity between hosts in our network happens entirely over WireGuard"; static routing; BPF swaps the host/network chunks of the address around WireGuard so cryptokey routing's non-overlapping AllowedIPs works ("swapping bytes in an IPv6 header doesn't alter checksums"); BPF programs also enforce "you can't talk to one 6PN network from another" ([ipv6-wireguard-peering](https://fly.io/blog/ipv6-wireguard-peering/), [6pn blog](https://fly.io/blog/incoming-6pn-private-networks/)). Kernel regression produced one-way WireGuard flows (Apr 14 2026) ([infra-log](https://fly.io/infra-log/)).

**.internal DNS.** A Rust DNS server on every host at `fdaa::3`, injected into resolv.conf, reachable only from the host's own 6PN via eBPF; backed by Corrosion (`corro-dns`) ([6pn blog](https://fly.io/blog/incoming-6pn-private-networks/), [infra-log](https://fly.io/infra-log/)). Names: `<app>.internal`, `<region>.<app>.internal`, `top<N>.nearest.of.<app>.internal`, `<machine_id>.vm.<app>.internal`, `<group>.process.<app>.internal`, `<value>.<key>.kv._metadata.<app>.internal`, `<peer>._peer.internal`; TXT: `vms.<app>.internal`, `all.vms...`, `regions...`, `_apps.internal`, `_instances.internal`. Only *started* Machines resolve ([private-networking docs](https://fly.io/docs/networking/private-networking/)). Bugs: CNAME cache without target (May 28 2026), ghost eBPF UDP entries after decommission (May 2024) ([infra-log](https://fly.io/infra-log/), [2024-05-25](https://fly.io/infra-log/2024-05-25/)).

**Flycast.** App-wide private IPv6 that routes *through fly-proxy*, so private callers get load balancing, autostart, TLS/PROXY handlers, and reachability while Machines are stopped; HTTP-only; app must bind 0.0.0.0 ([flycast docs](https://fly.io/docs/networking/flycast/)). It exists because direct 6PN "bypass[es] Fly Proxy" and because the Consul-era DNS lag made stale addresses a real problem ([foolish consistency](https://fly.io/blog/a-foolish-consistency/)).

**Ingress.** "We broadcast and accept traffic from ranges of IP addresses (both IPv4 and IPv6) in all our datacenters" (BGP Anycast); shared IPv4 + dedicated IPv6 per app ([architecture docs](https://fly.io/docs/reference/architecture/), [deploy docs](https://fly.io/docs/launch/deploy/)). Advertising a dev node broke public DNS anycast (Aug 20 2026) ([infra-log](https://fly.io/infra-log/)).

## 7. Storage

**Volumes.** "a slice of an NVMe drive on the same physical server as the Machine on which it's mounted"; LVM thin pool + ext4, LUKS ("pretty much rubber chicken security" in the 2020 post); 1:1 with a Machine; 1GB default, 500GB max, no shrink; daily block-level snapshots, 5-day default retention (1–60); "if the NVMe drive hosting your volume fails, then that instance of your app goes down"; "Always provision at least two volumes per app"; "resilience is your problem" ([volumes overview](https://fly.io/docs/volumes/overview/), [persistent-storage blog](https://fly.io/blog/persistent-storage-and-fast-remote-builds/)). Snapshot storage location is not stated. Rootfs is throttled to 2000 IOPS / 8 MiB/s; volume IOPS scale with Machine size (4k–32k) ([volumes overview](https://fly.io/docs/volumes/overview/)). Volumes force rolling (not canary/bluegreen) deploys ([seamless-deployments](https://fly.io/docs/blueprints/seamless-deployments/)).

**Why host-pinned, and the admission.** Performance and simplicity; but Sprites post: attached NVMe "anchors workloads to specific physicals" and it took "3 years of work for Fly Machines to support migration"; with object storage "the durable state of a Sprite is simply a URL" ([sprites design](https://fly.io/blog/design-and-implementation/)).

**LiteFS / Litestream.** LiteFS = FUSE proxy capturing SQLite transactions into LTX, Consul-leased primary ([introducing-litefs](https://fly.io/blog/introducing-litefs/)). Litestream revamp: S3 conditional writes give "time-based leases" so no Consul; LTX format; a VFS read replica that fetches pages from S3 ([litestream-revamped](https://fly.io/blog/litestream-revamped/)); a writable VFS with "eventual durability" syncing "every second or so", background hydration modelled on dm-clone, "Reads don't block on hydration" ([litestream-writable-vfs](https://fly.io/blog/litestream-writable-vfs/)). Fly's own control plane increasingly runs on this: tkdb, Sprites per-org DBs ([corrosion blog](https://fly.io/blog/corrosion/), [sprites design](https://fly.io/blog/design-and-implementation/)).

**Tigris.** S3-compatible partner store: FoundationDB metadata, "Fly.io's NVMe volumes as a first level of cached raw byte store", QuiCK-style replication, objects <~128KB "instantly global" ([tigris-public-beta](https://fly.io/blog/tigris-public-beta/)). Sprites' object store is "S3-compatible" (Tigris is not named as the backend in the design post).

**Sprites storage (the model pilots is closest to).** "a very hacked-up JuiceFS, with a rewritten SQLite metadata backend": immutable chunks on object storage, metadata "in fast local storage kept durable with Litestream", "a sparse 100GB NVMe volume attached ... a dm-cache-like feature" where "nothing in that NVMe volume should matter"; checkpoint and restore "merely shuffle metadata around"; billing per written block, TRIM reduces bill; block map "maybe low tens of megabytes worst case" loaded during boot ([sprites design](https://fly.io/blog/design-and-implementation/), [litestream-writable-vfs](https://fly.io/blog/litestream-writable-vfs/), [Willison summary](https://simonwillison.net/2026/Jan/9/sprites-dev/)). Limit they state: "performance isn't adequate for a hot Postgres node in production".

## 8. Builds & deploy

**Flow.** `fly deploy` = build (image from `--image`, `[build]`, Dockerfile, or buildpack) → push to `registry.fly.io` → create/update one or two Machines per process group (two by default "for redundancy") → allocate shared IPv4 + dedicated IPv6 ([deploy docs](https://fly.io/docs/launch/deploy/)). Registry is Fly's own wrapper of the Docker Go registry, content-addressed blobs, org-scoped repository rewriting ([docker-without-docker](https://fly.io/blog/docker-without-docker/)).

**Builders.** Legacy remote builder: a per-org Machine "with attached storage 'to cache layers and manifests'" exposing a Docker daemon, terminating "after 10 minutes of inactivity" ([persistent-storage blog](https://fly.io/blog/persistent-storage-and-fast-remote-builds/)). Since Sep 2024 the default is Depot: single-tenant Depot builders "run as Fly machines", cache "persisted to Fly volumes", image "pushed directly to Fly's internal registry", builder placed "geographically near the machine or CI provider"; 300 free build-minutes then $0.05/min; `--depot=false` fallback ([depot blog](https://depot.dev/blog/fly-builds-powered-by-depot), [community 21756](https://community.fly.io/t/depot-remote-builders-becoming-the-default/21756)). No build-time numbers are published.

**Strategies & gating.** `rolling` (default, `max_unavailable` count or %), `immediate`, `canary` (one new Machine first), `bluegreen` (all new Machines per region, switch after all pass health checks; "uses 2x resources briefly"; not with volumes); `release_command` runs in a throwaway Machine first ([seamless-deployments](https://fly.io/docs/blueprints/seamless-deployments/), [deploy docs](https://fly.io/docs/launch/deploy/)). Health checks: http (interval/timeout/grace_period/path), tcp, top-level `[checks]` (observability only, "don't influence routing"), and **machine checks** (throwaway Machine boots the new image with `FLY_TEST_MACHINE_IP`; "Fail the check, and the deploy halts"). "Smoke checks monitor Machines during deployment, for about 10 seconds after a Machine enters the started state" ([seamless-deployments](https://fly.io/docs/blueprints/seamless-deployments/)). Bluegreen had a public "machines never passing healthchecks" regression ([community 23483](https://community.fly.io/t/new-blue-green-deployments-failing-machines-never-passing-healthchecks/23483)).

**Deploy invalidates suspend snapshots** (new image = new rootfs = cold start) ([suspend-resume docs](https://fly.io/docs/reference/suspend-resume/)).

## 9. Multi-tenancy & security

**Isolation.** Firecracker ("the virtualization engine behind Amazon's Lambda and Fargate"), "written in Rust", "seccomp-bpf's itself down to something like 40 system calls" with argument filters, "Runs itself under an external jailer that chroots, namespaces, and drops privileges"; gVisor rejected on "a low-double-digits percentage hit, degrading with I/O load"; "the most important attack surface you need to reduce is exposure to your network" ([sandboxing post](https://fly.io/blog/sandboxing-and-workload-isolation/)). Hardware: "dedicated physical servers with 8-32 physical CPU cores and 32-256GB of RAM", with an attempt to dedicate cores to avoid steal ([architecture docs](https://fly.io/docs/reference/architecture/)). Volumes LUKS-encrypted per volume; two cryptsetup versions produced 4 MiB vs 16 MiB LUKS2 headers and thus different plaintext sizes during migration ([machine-migrations](https://fly.io/blog/machine-migrations/)). Network isolation via BPF on 6PN ([6pn blog](https://fly.io/blog/incoming-6pn-private-networks/)). Suspend snapshots are single-use "(security consideration)" ([preview thread](https://community.fly.io/t/new-feature-in-preview-suspend-resume-for-machines/20672)).

**GPUs.** Required Cloud Hypervisor (Firecracker "couldn't map hardware GPUs"), dedicated hosts, "hex-editing the closed-source drivers", two external security assessments; scaled back Feb 2025 because most devs call LLM APIs ([wrong-about-gpu](https://fly.io/blog/wrong-about-gpu/)). Not relevant to pilots except as a warning about hypervisor forks.

**Sprites vs Machines (2025–26).** Sprites: "Linux virtual machines where you get root", create "in just a second or two", "100GB durable root filesystem", auto-sleep, HTTPS URL on the Anycast network, checkpoints "so fast we want you to use them as a basic feature" ([sprites design](https://fly.io/blog/design-and-implementation/), [code-and-let-live](https://fly.io/blog/code-and-let-live/)). Structural differences from Machines: (a) no per-tenant image pull — "every physical worker knows exactly what container the next Sprite is going to start with, so it's easy for us to keep pools of 'empty' Sprites standing by"; (b) storage on object storage, not NVMe; (c) **"inside-out" orchestration** — "the most important orchestration and management work happens inside the VM" in the root namespace (storage stack, service manager, logging, `*:8080` binding), user code in an inner container, so platform changes have a blast radius of "just new VMs that pick up the change"; (d) control-plane metadata as per-org SQLite on object storage via Litestream, with Corrosion only for service discovery/URLs ([sprites design](https://fly.io/blog/design-and-implementation/)). Public numbers: create ~1s, sleep after 30s idle, checkpoint "~300ms", restore "about one second", last 5 checkpoints mounted at `/.sprite/checkpoints`, ~8 GB/8 CPU VMs, per-written-block billing ([code-and-let-live](https://fly.io/blog/code-and-let-live/), [Willison](https://simonwillison.net/2026/Jan/9/sprites-dev/), [checkpoint API](https://sprites.dev/api/sprites/checkpoints)). Checkpoints "capture only the writable overlay, not the base image" and are CoW/incremental with parent `source_id` ([checkpoint API](https://sprites.dev/api/sprites/checkpoints)). Sprites also plug into Corrosion for "instant public URL generation across the fleet" ([sprites design](https://fly.io/blog/design-and-implementation/)).

## Lessons pilots should COPY

1. **flyd's durable-FSM shape for hostd** (hostd machine lifecycle). Every lifecycle op (create, start, stop, suspend, checkpoint, restore, migrate) as an explicit FSM whose steps are journaled locally before execution, so a hostd restart mid-op resumes — "If we bounce flyd, it picks up right where it left off" ([carving](https://fly.io/blog/carving-the-scheduler-out-of-our-orchestrator/)). Fly deploys flyd daily because of this ([JP](https://fly.io/blog/the-exit-interview-jp/)). Bound the journal: flyd's "event store bloat" caused create timeouts ([infra-log](https://fly.io/infra-log/)).
2. **Synchronous, all-or-nothing placement with ordered fallbacks** (hostd API / any-host coordinator). "you're going to get VMs in MAD, or you're going to get nothing"; per-op ordered region/host list "tries each in order" ([carving](https://fly.io/blog/carving-the-scheduler-out-of-our-orchestrator/), [placement docs](https://fly.io/docs/machines/guides-examples/machine-placement/)). No pending queue state in the API.
3. **Best-fit *not* bin-pack** (placement ranking). Fly explicitly rejects bin packing for a platform that holds headroom — the "Katamari Damacy" failure ([carving](https://fly.io/blog/carving-the-scheduler-out-of-our-orchestrator/)). Rank hosts by "linear interpolation" over utilisation; pilots' `hash(key) mod live_hosts` for ownership is fine, but *placement* should consult live capacity.
4. **Treat cached images/templates as a placement resource** ([carving](https://fly.io/blog/carving-the-scheduler-out-of-our-orchestrator/)). Prefer the host that already has the template's chunks in NVMe cache; pilots' content-addressed S3 storage makes this cheap to expose as a per-host bitmap in Corrosion.
5. **Publish whole-row Machine state, never deltas** (hostd → Corrosion writer). Fly switched to "re-publish the entire data set for the Machine" to eliminate partial-update bugs ([corrosion blog](https://fly.io/blog/corrosion/)). One UPSERT of the full row per state change.
6. **Corrosion hygiene** (ops + schema): additive-only schema, defaults on every NOT NULL column ([schema doc](https://superfly.github.io/corrosion/schema.html)); **never add a column to a large table without a rollout plan** — CRDT backfill of every row took Fly down for a day ([2024-11-30](https://fly.io/infra-log/2024-11-30/)); deploy schema before consumers ([infra-log May 2026](https://fly.io/infra-log/)); set queue caps / gossip rate limits and OS-level egress limits on the corrosion unit ([2024-08-24](https://fly.io/infra-log/2024-08-24/), [2024-11-30](https://fly.io/infra-log/2024-11-30/)); keep daily Corrosion snapshots on S3 and a scripted re-seed from the source of truth (for pilots: hosts re-publish their own rows from local hostd state + S3) ([2024-10-26](https://fly.io/infra-log/2024-10-26/), [corrosion blog](https://fly.io/blog/corrosion/)); never let a retry loop write to Corrosion on backoff (150 GB/s storm) ([2024-10-26](https://fly.io/infra-log/2024-10-26/)); `ANALYZE` after bulk migrations ([infra-log Jun 2026](https://fly.io/infra-log/)).
7. **Watchdogs on every long-running loop** (hostd router, corrosion subscriber, DNS). "an event-loop stall will bounce the service and make a king-hell alerting racket"; the Dec 2024 recurrence was held to minutes by the watchdog ([corrosion blog](https://fly.io/blog/corrosion/), [2024-12-14](https://fly.io/infra-log/2024-12-14/)). Also: crash, don't hang — "the proxy hung rather than panicking" made Sep 1 worse ([2024-09-07](https://fly.io/infra-log/2024-09-07/)). systemd `Restart=always` + a liveness probe inside hostd.
8. **Bound the per-tenant blast radius of routing config** (hostd router). Validate customer-supplied routing state before it enters Corrosion; a single bad row hit every proxy fleet-wide ([2024-09-07](https://fly.io/infra-log/2024-09-07/)). For pilots this means: hostd parses/validates machine `services` rows defensively, and a malformed row is skipped, not fatal.
9. **Corrosion subscriptions with `from=` resume, bounded buffers** for the router's routing table; expect disconnect-on-lag and rebuild from a full query ([subscriptions doc](https://superfly.github.io/corrosion/api/subscriptions.html)). Fly's lazy loader shows the alternative (query-on-miss) has its own queueing failure ([infra-log May 2026](https://fly.io/infra-log/)); with pilots' single-host-scale fleet, full in-memory table + subscription is the simpler choice (inferred).
10. **Suspend semantics** (hostd suspend/wake): cap snapshot size (Fly: 2 GB, because full memory dump; consider diff snapshots for larger), fall back to cold boot when the snapshot is unusable, treat suspended machines as still reserving capacity, pace mass suspends (SYD I/O saturation), retry on the Firecracker API-socket bind/listen race, expect clock lag and dead TCP sessions in the guest and document it for tenants ([suspend-resume docs](https://fly.io/docs/reference/suspend-resume/), [threads](https://community.fly.io/t/autosuspend-is-here-machine-suspension-is-enabled-everywhere/20942), [more-reliable-resumes](https://community.fly.io/t/more-reliable-machine-resumes/26007), [infra-log](https://fly.io/infra-log/)). pilots' <500ms resume-gap target is in line with Fly's "a few hundred ms" / ~100–250ms.
11. **Load balancing model** (router N-replica): RTT-closest + `soft_limit`/`hard_limit` per machine, `type=requests` vs `connections`, queue then 503 at hard limit, and use soft-limit headroom as the autostart/autostop signal ([load-balancing docs](https://fly.io/docs/reference/load-balancing/), [autostop docs](https://fly.io/docs/launch/autostop-autostart/)).
12. **`fly-replay`-style app-directed routing** (router): a response header `{instance, prefer_instance, elsewhere, timeout, fallback}` with a 1 MB replay cap and a `-src` echo header is cheap and unlocks per-tenant sharding on one primitive ([dynamic-request-routing](https://fly.io/docs/networking/dynamic-request-routing/), [shared-nothing](https://fly.io/blog/shared-nothing)).
13. **Flycast idea** (`.internal` resolution): route private traffic *through* the router when the caller wants autostart/LB, and resolve only started machines in DNS ([flycast docs](https://fly.io/docs/networking/flycast/), [private-networking docs](https://fly.io/docs/networking/private-networking/)). pilots' `.internal` already resolves by name via Corrosion (#26); add the "via router" variant so a stopped service still has an address.
14. **Certificate issuance** (router ACME): tls-alpn-01 handled inside the router plus http-01, and refuse issuance unless DNS points at *your* IPs to block subdomain takeover ([how-cdns-generate-certificates](https://fly.io/blog/how-cdns-generate-certificates/)). pilots' DNS-01 wildcard + HTTP-01 per-domain matches this.
15. **Deploy gating** (rollout): smoke window after start, http/tcp checks with `grace_period`, machine checks that boot the new image in a throwaway VM before rollout, `release_command` in a throwaway VM, bluegreen as the fast/safe default when no volumes are involved ([seamless-deployments](https://fly.io/docs/blueprints/seamless-deployments/)).
16. **Sprites' inside-out orchestration and pre-warmed pools** (templates/instant create). Keep "pools of 'empty'" VMs booted from the one template every host knows; put storage stack, service manager, logging, and the `:8080` socket binder *inside* the guest so host-side changes have a blast radius of new VMs only ([sprites design](https://fly.io/blog/design-and-implementation/)). pilots' from-template restore <1.5s target is the same idea.
17. **Sprites' storage model validates pilots rule 4**: immutable chunks on object storage, small metadata map kept durable via Litestream, sparse NVMe read-through cache where "nothing in that NVMe volume should matter", checkpoints as metadata copies ([sprites design](https://fly.io/blog/design-and-implementation/), [litestream-writable-vfs](https://fly.io/blog/litestream-writable-vfs/)). Note the hydration trick: "Reads don't block on hydration" — serve from S3 immediately, switch to local when warm.
18. **Isolate control-plane-ish services from the data path** (per-host layout). Sep 1 2024 got worse because token validation went through the same proxies ([2024-09-07](https://fly.io/infra-log/2024-09-07/)); Fly's tkdb primary failure took down auth-dependent API ops ([infra-log Jul 2026](https://fly.io/infra-log/)). pilots: agent-token validation must be local (S3-cached keys), never a call to another host.
19. **Don't chain data-plane units on systemd ordering** (host-bootstrap). flyd and fly-proxy blocked on an nftables reload ([infra-log Aug 2026](https://fly.io/infra-log/)). hostd and corrosion must start independently and tolerate firewall reloads.
20. **Public infra-log.** The habit itself is a resilience tool; pilots should keep a `docs/incidents/` log from day one (inferred recommendation).

## What pilots should REJECT and why

- **Central API tier + Postgres + `flaps` broker.** Fly's create path does a "Preflight check with centralized Virginia database" and until Oct 2024 depended on Consul ([fly-machines blog](https://fly.io/blog/fly-machines/), [2024-10-26](https://fly.io/infra-log/2024-10-26/)); the Nov 2024 outage's second half was a Rails API jammed by SQL ([2024-11-30](https://fly.io/infra-log/2024-11-30/)). Violates pilots rule 1.
- **Central token/secret services (tkdb, Pet Sematary, Vault).** tkdb's primary host failure caused "widespread failures in API operations that depend on authentication" ([infra-log Jul 2026](https://fly.io/infra-log/)). pilots: keys and agent tokens in S3, validated locally.
- **One global flat Corrosion cluster for per-machine detail.** Fly's own verdict: "original sin"; they split into global (app→region) + regional (machine detail) ([corrosion blog](https://fly.io/blog/corrosion/), [2024-11-30](https://fly.io/infra-log/2024-11-30/)). pilots is single-region today; when multi-region arrives, plan the two-tier split up front rather than retrofitting.
- **Host-pinned volumes and host-encoded addresses.** Volumes: "resilience is your problem", 3 years to make migratable ([volumes overview](https://fly.io/docs/volumes/overview/), [sprites design](https://fly.io/blog/design-and-implementation/)). 6PN embeds the host id, which migration broke and required DNAT shims and a "stable 6PN" rewrite ([machine-migrations](https://fly.io/blog/machine-migrations/), [infra-log Jun 2026](https://fly.io/infra-log/)). pilots' constant guest addresses + host-agnostic snapshots (rule 5) are the right call; never leak a host id into a name, URL, or guest address.
- **Per-tenant OCI image pull as the create path.** "Most of what's slow about creating a Fly Machine is containers" ([sprites design](https://fly.io/blog/design-and-implementation/)). pilots' deploy should build to a content-addressed rootfs in S3 once and let every host lazy-fetch chunks; never `docker pull` on the create path.
- **Non-durable, single-use suspend snapshots.** Fly: "Suspend is not durable"; deploy or migration → cold start ([suspend-resume docs](https://fly.io/docs/reference/suspend-resume/)). pilots' durable async checkpoints to S3 are strictly better; keep them.
- **NBD for live block migration.** Fly abandoned it for iSCSI because of "stuck nbd kernel threads" on network hiccups ([machine-migrations](https://fly.io/blog/machine-migrations/)). pilots' NBD handler is a *local* userspace block backend (port from pilots-old), not a network path; do not extend it across hosts.
- **Guest-side idle detection as the only mechanism.** Fly's original advice ("exit when idle") pushes lifecycle into tenant code ([fly-machines blog](https://fly.io/blog/fly-machines/)); pilots' router-driven idle-suspend (timer AND concurrency) is the parity target, per ARCHITECTURE.md.
- **Edges/workers split and Anycast BGP.** Requires ASN, IP blocks, peering. pilots uses wildcard DNS to all host IPs on one apex (rule 5); revisit only if multi-region latency demands it.
- **Load gossip over a separate NATS bus.** Extra process per host; pilots' router can read concurrency counts from the same Corrosion rows hostd already publishes (inferred; Fly kept NATS for volatility reasons, which matter less at pilots' scale).

## What pilots ALREADY has at parity or better (vs ARCHITECTURE.md rules 1–7)

| Rule | pilots | Fly | Verdict |
|---|---|---|---|
| 1 No central control plane | every host serves the full API | flaps is stateless but Rails/Postgres, tkdb, registry are central; three 2024 outages came from central or global-flat pieces | pilots better by design; must not regress by adding a "dashboard host" dependency to any request path |
| 2 Three processes per host | hostd + corrosion + firecracker | flyd + fly-proxy + corrosion + corro-dns + udpcatalogd + containerd + NATS + attache/consul-agent (legacy) | pilots simpler; Fly's systemd-ordering and OOM incidents argue for keeping it that way |
| 3 State = Corrosion, single-writer | enforced in review | same model ("workers own their own state"), broken once by migration | parity; copy whole-row publish + additive schema discipline |
| 4 S3 is the only truth, NVMe a cache | design test "wipe any host's disk" | Machines: no (host-pinned volumes, containerd cache is authoritative for the rootfs); Sprites: yes, "the durable state of a Sprite is simply a URL" | pilots at parity with Sprites, ahead of Machines |
| 5 URLs permanent, host-agnostic snapshots | `<name>.pilotrun.app`, constant guest addressing | Machine IDs stable but 6PN addresses host-encoded; suspend snapshots die on migration | pilots better |
| 6 CPU-vendor-homogeneous fleet | pinned cpu_template | not documented publicly; suspend "will cold-start if migrated to different hosts" avoids the problem | pilots explicit where Fly is silent |
| 7 Fly-shaped orchestration, sprites-shaped storage | per-host autonomy + any-host coordination; content-addressed storage | exactly Fly's flyd/flaps split and Sprites' JuiceFS-style store | parity by construction; the missing Fly piece is the ordered-fallback placement API and best-fit ranking |

Capabilities table cross-check: instant create <1.5s (Sprites ~1s, Machines "over a minute" create / ~300ms start); resume-gap <500ms (Fly "a few hundred ms"); wake <1s as a held request (Fly does this via fly-proxy; no waiting page documented); self-heal with zero human action (Fly has none for Machines — "resilience is your problem"); durable named chained checkpoints (Sprites yes ~300ms/~1s, Machines no); volumes surviving host death (Fly no, Sprites yes).
